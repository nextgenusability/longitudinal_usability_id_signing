SECTION 1: PROJECT CONTEXT
================================================================================

--- 1.1 Study Overview ---

This study empirically examines the usability lifecycle of identity-based software signing tools by analyzing how usability concerns evolve in public GitHub issue discussions. Issues and their follow-on comments are treated as a time-stamped record of reported challenges. The study analyzes 3,901 issues over a 48-month window (ending November 5, 2025) across five identity-based signing ecosystems:

- Sigstore (cosign, fulcio, rekor)
- OpenPubKey
- HashiCorp Vault
- Keyfactor (EJBCA, SignServer CE)
- Notary v2 (Notation)

Each issue is coded for: (1) the type of usability concern it reflects, and (2) the tool component(s) implicated by the report and its discussion.

--- 1.2 Background: Identity-Based Signing Tools ---

Unlike legacy key-managed signing (e.g., OpenPGP), which relies on long-lived key pairs managed by the signer, identity-based signing tools delegate key management responsibility to an ecosystem of components:

- Orchestrator: the primary CLI/interface developers use to sign and verify artifacts (e.g., cosign, notation)
- Identity Provider (IdP): authenticates the signer and issues an identity token (e.g., Okta, GitHub-based OIDC)
- Certificate Authority (CA) / Credential Issuer: binds identity to a short-lived signing credential (e.g., Fulcio, EJBCA)
- Transparency / Signature Logs: append-only logs for audit and verification support (e.g., Rekor)

This modular design reduces key-handling burden but expands the configuration surface and introduces cross-component usability friction at integration boundaries.

--- 5.1 Associated Component ---

Capture which part of the tool the issue is about — the surface that must change for the issue to be resolved.

Rules:
- Record: tool name + relevant component/functionality.
  Examples:
    - Keyfactor EJBCA (Certificate Authority) - Web Client
    - HashiCorp Vault - Authentication
    - Keyfactor EJBCA (Certificate Authority) - Email/User Notification System
    - HashiCorp Vault - Authentication, CLI

- If you cannot identify the specific component, or the issue affects the entire tool, use:
  [tool name] core
  Example: cosign core

- If the issue is about a CLI command (e.g., "vault sign", "cosign tree"), label it as CLI in addition to any other relevant component.

- If the affected surface is external to the tool (e.g., cosign being integrated into Vault's key store), do not record the external system. Use the tool's core instead.
  Example: use "cosign core" not "cosign - S3 bucket"

- Treat Docker/container images as installation/distribution aids. Label as "installation/distribution", not as an external component.

- Do not use packaging/dependencies as components (these are implementation details).

- If multiple components are involved, list all, comma-separated.

--- 5.2 codes_primary ---

Write a short prose summary (30-50 words; more only if clearly warranted) of what the reporter is experiencing or requesting and its effect (if stated).

Rules:
- Preserve stance: label as question/confusion, feature request/enhancement, or report of unexpected behavior/bug.
- For feature requests: note whether the request was motivated by a challenge or use case the user is currently facing.
- Include key context: mentions of following documentation, links to other issues/guides, integration context, reproducibility, or lack of context.
- For compatibility/integration issues: use keywords like "compatible" or "integration" to flag the nature clearly.
- Do not include GitHub issue template boilerplate text in your summary.

Example codes_primary:
"Docker image issue prevents the web client from being installed. User reports this is reproducible and is unsure if they are doing something wrong. A workaround was suggested by maintainers to make the installation work."

SECTION 6: PHASE 2 — USABILITY VS. NON-USABILITY CLASSIFICATION
================================================================================

--- 6.1 Definitions ---

USABILITY (value = 1):
Any issue where the software is technically functional (it did not crash due to a bug), but the user failed to achieve their goal efficiently, effectively, or satisfactorily due to the design, interface, feedback, or documentation.

NON-USABILITY (value = 0):
Pure functional bugs (e.g., null pointer exceptions, incorrect cryptographic calculations), feature requests that are entirely new capabilities outside current scope and not motivated by a user problem, or infrastructure/maintenance tasks.

--- 6.2 Decision Rules: Usability Indicators ---

Classify as USABILITY (1) if any of the following apply:

- The reporter is asking a question or expressing confusion about how the tool works.
- The issue involves someone following documentation and not achieving expected outcomes.
- The issue is about error messages, logging, or notifications not being informative or actionable enough.
- The issue is a Web UI/Client concern.
- The feature request is motivated by a current challenge, workflow blocker, or confusion the user is experiencing (not merely "it would be nice if...").
- The issue contains aspects of both usability and non-usability — default to usability.

--- 6.3 Decision Rules: Non-Usability Indicators ---

Classify as NON-USABILITY (0) if any of the following apply:

- The program stopped running unexpectedly, entered an invalid state, or produced a mathematically/logically incorrect result (a crash, panic, null pointer, cryptographic failure).
- The software entered a state where it could no longer function due to resource mismanagement.
- The issue is a "blue sky" feature request with no described problem motivating it (e.g., "it would be cool if...").
- The error cannot be reproduced by the user and may be caused by environmental factors.
- The issue provides no detail suggesting user confusion or understanding difficulties, and has no clarifying comments — default to non-usability.

--- 6.4 Diagnostic Question ---

Ask yourself: "Did the program stop running unexpectedly, enter an invalid state, or produce a mathematically/logically incorrect result?"

  YES -> Non-Usability (0)
  NO (it ran, but the experience was confusing or frustrating) -> Usability (1)

--- 6.5 Contrast Examples ---

CONTRAST SET A: The Failed Validation

Non-Usability example:
"I signed this image using the standard workflow. When I run verify, it says Error: Crypto/RSA verification failed. I have triple-checked keys. The signature generation seems broken."
Reasoning: The core mathematical function of the tool is not working. -> NON-USABILITY

Usability example:
"I tried to verify an image. It said Error: verification failed. I spent 3 hours debugging and realized I was pointing to the wrong public key file. The error message should have told me the key didn't match the format, rather than just a generic fail."
Reasoning: The tool worked correctly — it rejected a wrong key. The failure was in the messaging (error diagnosis), which caused user friction. -> USABILITY

CONTRAST SET B: The Program Stopping

Non-Usability example:
"When I run the command with the --verbose flag, it instantly crashes and dumps a stack trace."
Reasoning: The code accessed memory it shouldn't. It broke. -> NON-USABILITY

Usability example:
"When I run the command, it prints 'Error: missing argument' and exits immediately. I had to read the source code to figure out which argument was missing."
Reasoning: The program stopped intentionally because of bad input. It didn't crash. It just provided terrible feedback. -> USABILITY

--- 6.6 Tool-Specific Notes ---

OpenPubKey:
- Use issue labels (e.g., "enhancement") to confirm feature requests when body_text lacks a template.
- OP = OpenPub (e.g., OP client = OpenPub client). OPK = OpenPubKey.

Sigstore-Cosign:
- Some issues are internal team tracking discussions, not usability issues. Watch for these.
- Issues labeled "question" or with question-format titles = treat as confused user questions = usability.
- For enhancement-labeled issues: treat the title as the requested feature and body_text as the motivating challenge context.
- If a bug report also shows user confusion, documentation following, or questions — treat as usability.
- Abbreviation: FR = Feature Request.

SECTION 7: PHASE 3 — NIELSEN'S USABILITY HEURISTIC THEMES
================================================================================

APPLIES TO: Only usability issues (usability_non-usability_type = 1).
Multiple labels allowed; separate with commas.
Use codes_primary as primary anchor; re-read body_text/comments when needed.

NOTE: Integration with external tools always counts as Nielsen #7 (Flexibility and Efficiency of Use) and may co-occur with other Nielsen themes.

---

HEURISTIC 1: Visibility of System Status
Definition: The system keeps users informed about what is going on through timely feedback.
Identify when: User is unsure if the tool is working, frozen, or finished. System gives no output or unclear non-error output.
Example markers: "The command just hung with no output", "I didn't know if the upload succeeded", "Needs a progress bar for long operations."

---

HEURISTIC 2: Match Between System and the Real World
Definition: The design speaks the user's language, using familiar words and concepts rather than internal jargon.
Identify when: Confusion caused by the tool using internal terminology instead of standard industry terms.
Example markers: "What does [obscure internal term] mean in the flag description?", "Why is this called X when everyone else calls it Y?", "The error message exposed internal variable names."

---

HEURISTIC 3: User Control and Freedom
Definition: Users need a clearly marked emergency exit to leave unwanted states. Supports undo and redo.
Identify when: Users feel trapped in a process or cannot easily reverse an action.
Example markers: "I couldn't cancel the operation with Ctrl+C", "I accidentally signed the wrong artifact and can't undo it", "Need a dry-run flag before performing destructive actions."

---

HEURISTIC 4: Consistency and Standards
Definition: Users should not have to wonder whether different words or actions mean the same thing. Follow platform and industry conventions.
Identify when: Complaints that the tool behaves differently from other tools in the ecosystem, is internally inconsistent, or counterintuitive to use.
Example markers: "This flag works differently here than it does in Docker", "Why does command A use --file but command B uses --path?", "Does not follow POSIX standards for arguments."

---

HEURISTIC 5: Error Prevention
Definition: Good design prevents problems before they happen; presents confirmation options before committing to destructive actions.
Identify when: Users fall into traps the system could have easily identified beforehand. Users ask about consequences of performing an action.
Example markers: "The tool let me upload an invalid signature file without warning", "Should prompt for confirmation before overwriting", "Allowed me to use an expired key."

---

HEURISTIC 6: Recognition Rather Than Recall
Definition: Minimize memory load by making elements, actions, and options visible. Users shouldn't need to remember information across parts of the interface.
Identify when: Complaints about how much users must memorize vs. being prompted. High cognitive load placed on users to complete a task.
Example markers: "I have to constantly check the docs for basic flag syntax", "Lack of tab-completion makes this hard to use", "Help output doesn't show required arguments clearly."

---

HEURISTIC 7: Flexibility and Efficiency of Use
Definition: Design caters to both inexperienced and experienced users; allows tailoring of frequent actions.
Identify when: Workflow blockers. Power users cannot automate/script; new users find simple tasks too complex. Integration limitations with other tools.
Example markers: "Too many steps for a simple sign operation", "Need JSON output so I can pipe this into another tool", "Cannot configure defaults for repetitive flags."

---

HEURISTIC 8: Aesthetic and Minimalist Design
Definition: Interfaces should not contain irrelevant or rarely needed information. Every extra unit competes with relevant information.
Identify when: Complaints about noisy output hiding the actual result the user cares about, or UI/UX friction on the web client.
Example markers: "The default output is too verbose", "Debug logs are printed by default, obscuring the success message", "Help text is a wall of text and hard to scan."

---

HEURISTIC 9: Help Users Recognize, Diagnose, and Recover from Errors
Definition: Error messages should be in plain language, precisely indicate the problem, and constructively suggest a solution.
Identify when: Reports of terse or useless error messages. User cannot tell what went wrong or how to fix it.
Example markers: "The tool just failed with 'Error 500' and no context", "The error message didn't tell me how to fix the certificate issue", "Printed a raw stack trace instead of a human-readable message."
Note: If the issue is about missing information generally (not an error message), use Heuristic 10 instead.

---

HEURISTIC 10: Help and Documentation
Definition: While systems should ideally be self-explanatory, documentation must help users understand how to complete their tasks.
Identify when: Explicit complaints about the quality, existence, or accuracy of the documentation (README, website, or CLI --help text).
Example markers: "The examples in the README don't work", "Documentation is outdated compared to the current CLI version", "Cannot find info on how to use this feature with private registries."

SECTION 8: PHASE 4 — L1_THEME (DETAILED LOW-LEVEL THEMES)
================================================================================

APPLIES TO: Only usability issues (usability_non-usability_type = 1).
Multiple themes per issue are allowed; separate with commas.
Anchor in codes_primary; re-read body_text/comments when needed.

---

L1 THEME 1: Missing Feature / Enhancement Request
Description: The user is asking for functionality that does not currently exist, or to enhance existing functionality (except documentation).
Example: "Add support for Ed25519 keys."

---

L1 THEME 2: Unexpected Behavior
Description: The software behaves incorrectly (errors) despite the user following instructions or documentation.
Example: User followed documented steps exactly but received an unexpected result or error.

---

L1 THEME 3: Authentication Friction
Description: The user is unable to log in or authenticate successfully due to token errors, timeouts, or confusing flows. Includes OIDC, MFA, authorization, user groups, and identification issues.
Example: "Token refresh failed", "401 Unauthorized loop."

---

L1 THEME 4: Configuration Friction
Description: The user is struggling to configure the software correctly due to complex setups, rigid settings, or issues that are resolved by correct configuration.
Example: User cannot figure out the correct YAML/JSON configuration to enable a feature.

---

L1 THEME 5: Integration Failure / Issues
Description: The tool fails to interoperate with an external system (a specific Cloud KMS, Registry, or IdP) despite correct configuration. Includes requests for new external integrations.
IMPORTANT: Issues between components of the same tool ecosystem are NOT integration issues. For example, a Fulcio integration issue within cosign is not an integration issue; a cosign integration issue with an external S3 bucket is.
Example: "Azure KeyVault plugin timeout", "Docker Registry API 404."

---

L1 THEME 6: User Confusion / Unclear Documentation / Documentation Improvements
Description: The user does not understand how to use the tool (asking questions or confused), the documentation misleads or is insufficient, or there is a need to improve documentation.
Example: "How do I sign a blob?", "Docs say flag X exists but it doesn't."

---

L1 THEME 7: Build/CI/Installation/Distribution Release Issues
Description: The tool fails to run or install in an automated environment, fails to compile, or the distribution release cannot be assessed/installed.
Example: "Go toolchain version mismatch", "CI pipeline fails on test."

---

L1 THEME 8: Performance Issue
Description: The tool is functionally working but is too slow, consumes too much memory, or has high latency. Includes enhancement requests to address these deficiencies.
Example: "Verification takes 30 seconds."

---

L1 THEME 9: Security Concerns
Description: A report of a vulnerability (CVE), an unsafe default, or a request to harden security posture.
Example: "Weak crypto default", "Secret leaked in logs."

---

L1 THEME 10: Notification / Logging / Web UI Issues
Description: Issues regarding error messages, logging messages, or Web UI (web client) feedback that are not helpful in resolving problems, or similar concerns.
Example: Notification text is unclear; log output does not indicate root cause; web client UI is difficult to navigate.

---

L1 THEME 11: Tedious Workflows
Description: Users must perform many operations to achieve one purpose; the tool imposes too many requirements to accomplish a task.
Example: "I have to run 5 separate commands just to sign a single artifact."

SECONDARY BUCKET 1: Operational Friction
Description: Barriers involving setup, environment, integration, or workflow execution. The user knows what to do, but the tool/environment resists.
Mapped L1_Themes:
  - Configuration Friction
  - Authentication Friction
  - Build/CI/Installation/Distribution Release Issues
  - Integration Failure/Issues
  - Tedious Workflows

---

SECONDARY BUCKET 2: Cognitive Friction
Description: Barriers related to understanding, mental models, or clarity. The user stops because they don't know how to proceed or the tool is confusing.
Mapped L1_Themes:
  - User Confusion / Unclear Documentation
  - Notification/Logging Issues

---

SECONDARY BUCKET 3: Functional Reliability
Description: Friction caused when the tool fails to perform its promised function due to bugs, slowness, or security risks.
Mapped L1_Themes:
  - Unexpected Behavior
  - Performance Issue
  - Security Concerns

---

SECONDARY BUCKET 4: Functional Gap
Description: The tool currently lacks the capability to perform the user's desired task.
Mapped L1_Themes:
  - Missing Feature / Enhancement Request

Description: Issues specific to the command-line interface as the point of interaction. Flag parsing logic, help output text, terminal UX, output formatting (JSON vs text), interactive prompts.

---

COMPONENT THEME 3: Signing Workflow
Description: The end-to-end client-side process a user performs to cryptographically sign an artifact.
Applies to: Issues where the key idea is that the user is trying to sign.

---

COMPONENT THEME 4: Verification Workflow
Description: The end-to-end client-side process a user performs to validate a signature.
Applies to: Issues where the key idea is that the user is trying to verify.

---

COMPONENT THEME 5: Policy / Configuration
Description: How the tool is configured by the user or administrator. Includes syntax/logic issues in config files (YAML/JSON), defining and enforcing security policies (OPA/Rego), and interpretation of settings.

---

COMPONENT THEME 6: Build / CI / Installation
Description: Friction when running, installing, or using the tool in automated, non-interactive environments (CI/CD pipelines, containerized builds, automated scripts).

COMPONENT THEME 7: Release Pipeline
Description: Issues related to how project maintainers build, sign, and publish official releases, binaries, and artifacts of the tools themselves.

COMPONENT THEME 10: API

Applies to: User interacting with the tool's API, not CLI or UI.

---

COMPONENT THEME 11: Web Client
Description: Issues affecting the web UI, client, or admin dashboard of these tools.

Description: Infrastructure for secure storage, generation, retrieval, and lifecycle management of cryptographic keys and secrets. Covers integrations with external KMS (HashiCorp Vault, AWS KMS, GCP KMS), HSMs, and local secure storage (keychains, YubiKeys).

SECTION 11: TRAINING PHASES & ANNOTATION PROCESS
================================================================================

Annotation is conducted in sequential phases with iterative calibration between human annotators and you (the LLM classifier). The goal is to reach agreement before coding the held-out evaluation set.

PHASE 1
Target columns: Associated Component, codes_primary
Process: Train on the first 100 issues in batches of 25. Output your labels; receive human feedback; iterate until alignment is satisfactory. Then review the 100 labelled issues. Finally, code the held-out 60 issues (issues 102-161) for agreement measurement.

PHASE 2
Target column: usability_non-usability_type
Process: Follow the same batch training process. Label issues as usability (1) or non-usability (0). Calibrate against human labels before final coding.

PHASES 3-5
Target columns: L1_Theme, L1_Theme Secondary, Associated Component Theme, Nielsen_Theme
Process: Follow the same process for each column in turn. Only label usability issues. Multiple labels per column are allowed.
