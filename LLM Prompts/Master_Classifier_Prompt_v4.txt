SECTION 1: PROJECT CONTEXT
================================================================================

--- 1.1 Study Overview ---

This study empirically examines the usability lifecycle of identity-based software signing tools by analyzing how usability concerns evolve in public GitHub issue discussions. Issues and their follow-on comments are treated as a time-stamped record of reported challenges. The study analyzes 3,901 issues over a 48-month window (ending November 5, 2025) across five identity-based signing ecosystems:

- Sigstore (cosign, fulcio, rekor)
- OpenPubKey
- HashiCorp Vault
- Keyfactor (EJBCA, SignServer CE)
- Notary v2 (Notation)

Each issue is coded for: (1) the type of usability concern it reflects, and (2) the tool component(s) implicated by the report and its discussion.

--- 1.2 Background: Identity-Based Signing Tools ---

Unlike legacy key-managed signing (e.g., OpenPGP), which relies on long-lived key pairs managed by the signer, identity-based signing tools delegate key management responsibility to an ecosystem of components:

- Orchestrator: the primary CLI/interface developers use to sign and verify artifacts (e.g., cosign, notation)
- Identity Provider (IdP): authenticates the signer and issues an identity token (e.g., Okta, GitHub-based OIDC)
- Certificate Authority (CA) / Credential Issuer: binds identity to a short-lived signing credential (e.g., Fulcio, EJBCA)
- Transparency / Signature Logs: append-only logs for audit and verification support (e.g., Rekor)

This modular design reduces key-handling burden but expands the configuration surface and introduces cross-component usability friction at integration boundaries.

SECTION 6: PHASE 2 — USABILITY VS. NON-USABILITY CLASSIFICATION
================================================================================

--- 6.1 Definitions ---

USABILITY (value = 1):
Any issue where the software is technically functional (it did not crash due to a bug), but the user failed to achieve their goal efficiently, effectively, or satisfactorily due to the design, interface, feedback, or documentation.

NON-USABILITY (value = 0):
Pure functional bugs (e.g., null pointer exceptions, incorrect cryptographic calculations), feature requests that are entirely new capabilities outside current scope and not motivated by a user problem, or infrastructure/maintenance tasks.

--- 6.2 Decision Rules: Usability Indicators ---

Classify as USABILITY (1) if any of the following apply:

- The reporter is asking a question or expressing confusion about how the tool works.
- The issue involves someone following documentation and not achieving expected outcomes.
- The issue is about error messages, logging, or notifications not being informative or actionable enough.
- The issue is a Web UI/Client concern.
- The feature request is motivated by a current challenge, workflow blocker, or confusion the user is experiencing (not merely "it would be nice if...").
- The issue contains aspects of both usability and non-usability — default to usability.

CRITICAL — ENHANCEMENT ISSUES (most commonly missed):
Enhancement/feature request issues are very frequently USABILITY even when they look purely technical. Apply this rule:
  If the enhancement is motivated by a workflow problem, a limitation the user has hit, or friction in how they
  currently use the tool — it is USABILITY.
  If it is purely "blue sky" with no described friction — it is NON-USABILITY.

  Apply this test: "Is the reporter describing something the tool currently makes hard, impossible, or confusing
  to do?" If yes → USABILITY, regardless of whether the label says "enhancement" or "feature request."

Examples of enhancements that ARE usability:
  - "Add support for verifying by JTK in VerifyProvider if not kid is found" — user hit a real gap in the current flow.
  - "Singleton to manage user's browser window" — user describes the current multi-tab behavior as a problem.
  - "[cosigned] Enforce authority key errors" — user says current behavior (silent warnings) causes confusion.
  - "Require embedded SCT on verification by default" — user identifies a security/workflow gap.
  - "Cleanup KeyOpts for irrelevant options" — user says the current options structure is confusing.

CRITICAL — BUG ISSUES THAT ARE ACTUALLY USABILITY:
A bug report is USABILITY (not non-usability) when:
  - The user followed documentation or a guide and still got the error. Even if a bug is confirmed, the fact
    that the user was following docs and got an unexpected result is a usability failure.
  - The user expresses confusion about whether they did something wrong.
  - The resolution involves documentation improvement, a workaround being communicated, or a config change
    (not a code fix to a broken function).

Example:
  "make cosign fails with malformed module path" — labeled bug, but user followed the Makefile documentation
  and admin confirmed docs were fixed. This is a usability issue (build/CI friction + documentation).

CRITICAL — INTERNAL/MAINTAINER ISSUES (the most persistent error pattern):
The classification depends on the SUBJECT of the issue, not on who opened it or whether a user is
explicitly quoted as confused. Ask: "Does the subject of this issue directly affect how users
experience or interact with the tool?" If yes → USABILITY, even if no individual user complaint
is attached and even if a maintainer opened it.

Apply this subject-based test to common maintainer issue types:

  Documentation cleanup/improvement (fixing spec files, updating README, adding doc pointers)
  → USABILITY. Users reading incorrect or missing docs is a usability failure.
  Example: "Clean up blob sign/verify specs in v1.1.1" → usability (documentation improvements).

  Integration/capability expansion (support other KMS providers, new flag to load key from file)
  → USABILITY. Users on unsupported platforms are blocked. This is a capability/integration gap.
  Example: "Support other KMS keys besides GCP" → usability (integration issues, enhancement request).

  Performance improvements (faster JSON marshalling, reduced latency)
  → USABILITY. Users experience the slowness directly.
  Example: "Investigate using custom JSON parser" → usability (performance issue).

  Spec compliance / interoperability fixes (align key ID computation with published spec)
  → USABILITY. Users' downstream tools break if the tool is non-compliant.
  Example: "Checkpoint spec compliance: Incorrect key ID for non-ECDSA keys" → usability.

  Logging/retrieval gaps (log entries not returned due to missing field)
  → USABILITY. Users cannot retrieve their own data.
  Example: "attestations for intoto log entries without payloadHash not being returned" → usability.

  Pure internal refactors (rename a private variable, move code between files, change a build
  dependency with zero user-visible effect) → NON-USABILITY.

The deciding question is: does the change, if made, affect something a user touches, sees,
or depends on?
  YES → USABILITY
  NO  → NON-USABILITY

--- 6.3 Decision Rules: Non-Usability Indicators ---

Classify as NON-USABILITY (0) if any of the following apply:

- The program stopped running unexpectedly, entered an invalid state, or produced a mathematically/logically incorrect result (a crash, panic, null pointer, cryptographic failure).
- The software entered a state where it could no longer function due to resource mismanagement.
- The issue is a "blue sky" feature request with no described problem motivating it (e.g., "it would be cool if...").
- The error cannot be reproduced by the user and may be caused by environmental factors.
- The issue provides no detail suggesting user confusion or understanding difficulties, and has no clarifying comments — default to non-usability.
- The issue is purely an internal infrastructure task, code refactor, or CI/build pipeline change with NO described user-facing friction or impact.

DO NOT classify as non-usability just because:
  - The issue is labeled "enhancement" or "bug"
  - The issue was opened by a maintainer
  - The issue references internal code details
  - The issue looks technical
  These are surface signals. Always look for whether user-facing friction is described.

--- 6.4 Diagnostic Questions ---

PRIMARY: "Did the program stop running unexpectedly, enter an invalid state, or produce a mathematically/logically incorrect result?"
  YES -> Non-Usability (0)
  NO (it ran, but the experience was confusing or frustrating) -> Usability (1)

SECONDARY (use when the primary question is unclear): "Does the subject of this issue — what it is about — directly affect something a user touches, sees, or depends on when using the tool?"
  YES -> Usability (1), regardless of whether a user explicitly complained or a maintainer opened it.
  NO (the subject is purely internal with no user-visible effect) -> Non-Usability (0)

--- 6.5 Contrast Examples ---

CONTRAST SET A: The Failed Validation

Non-Usability example:
"I signed this image using the standard workflow. When I run verify, it says Error: Crypto/RSA verification failed. I have triple-checked keys. The signature generation seems broken."
Reasoning: The core mathematical function of the tool is not working. -> NON-USABILITY

Usability example:
"I tried to verify an image. It said Error: verification failed. I spent 3 hours debugging and realized I was pointing to the wrong public key file. The error message should have told me the key didn't match the format, rather than just a generic fail."
Reasoning: The tool worked correctly — it rejected a wrong key. The failure was in the messaging (error diagnosis), which caused user friction. -> USABILITY

CONTRAST SET B: The Program Stopping

Non-Usability example:
"When I run the command with the --verbose flag, it instantly crashes and dumps a stack trace."
Reasoning: The code accessed memory it shouldn't. It broke. -> NON-USABILITY

Usability example:
"When I run the command, it prints 'Error: missing argument' and exits immediately. I had to read the source code to figure out which argument was missing."
Reasoning: The program stopped intentionally because of bad input. It didn't crash. It just provided terrible feedback. -> USABILITY

CONTRAST SET C: The Enhancement Request (most commonly misclassified)

Non-Usability example:
"It would be cool if we added support for Ed448 curve keys eventually."
Reasoning: No described friction. Blue sky. -> NON-USABILITY

Usability example:
"Add support for verifying by JTK in VerifyProvider if not kid is found — some OIDC providers omit kid, so our users cannot verify at all with these providers."
Reasoning: User describes a concrete workflow blocker caused by the current tool's behavior. -> USABILITY

Usability example:
"Singleton to manage user's browser window — the OP client currently spins up multiple redirect tabs which is hard to manage."
Reasoning: Reporter describes the current behavior as a problem (multi-tab confusion). Enhancement motivated by friction. -> USABILITY

CONTRAST SET D: The Maintenance / Internal Issue

Non-Usability example:
"Refactor the internal logging subsystem to use zerolog instead of zap."
Reasoning: Pure internal code change, no user-facing impact described. -> NON-USABILITY

Usability example:
"verify* subcommands should share signature verification flag parsing — there is duplicated and almost-duplicated code across verify, verify-blob, verify-attestation subcommands, causing inconsistent behavior for users."
Reasoning: Technical refactor, but the motivation is user-visible inconsistency. -> USABILITY

CONTRAST SET E: The Bug That Is Also Usability

Non-Usability example:
"Cosign crashes with null pointer exception when signing with --key flag pointing to a non-existent file."
Reasoning: Unexpected crash, invalid state. -> NON-USABILITY

Usability example:
"make cosign fails with malformed module path — I followed the README instructions to build with PIV support. The admin confirmed the docs were updated but this still fails."
Reasoning: User followed documentation, hit a failure. Even though it's labeled a bug, the documentation-following + friction context makes this usability. -> USABILITY

CONTRAST SET F: The Maintainer-Opened Issue (most persistent error — read carefully)

Non-Usability example:
"Rename internal variable signerOpts to signerOptions throughout the codebase for consistency."
Reasoning: Pure internal rename. No user touches this. Zero user-visible effect. -> NON-USABILITY

Usability example:
"add info to readme file to point out other doc files"
Reasoning: Subject is documentation discoverability. Users who cannot find the right docs are
experiencing a usability failure. Maintainer opened it, no user complained — irrelevant.
The SUBJECT affects users. -> USABILITY

Usability example:
"Support other KMS keys besides GCP"
Reasoning: Subject is an integration gap. Users on AWS KMS or Azure KMS are blocked entirely.
No user is quoted — irrelevant. The SUBJECT affects users. -> USABILITY

Usability example:
"attestations for intoto log entries persisted without payloadHash are not being returned"
Reasoning: Subject is data retrieval. Users who stored these entries cannot retrieve them.
Framed as a bug, no confused user quoted — irrelevant. The SUBJECT is a capability failure
users experience directly. -> USABILITY

Usability example:
"Checkpoint spec compliance: Incorrect key ID for non-ECDSA keys"
Reasoning: Subject is interoperability. Users' downstream witnesses break because the tool
produces non-compliant output. Maintainer opened it — irrelevant. SUBJECT affects users. -> USABILITY

SECTION 7: PHASE 3 — NIELSEN'S USABILITY HEURISTIC THEMES
================================================================================

APPLIES TO: Only usability issues (usability_non-usability_type = 1).
Use codes_primary as primary anchor; re-read body_text/comments when needed.

IMPORTANT — Do not leave Nielsen themes blank for usability issues: If you have classified an issue as usability,
you MUST assign at least one Nielsen theme. There is no valid usability issue with no applicable heuristic.
If the issue is about documentation or user confusion, assign at minimum Heuristic 10. If it involves a workflow
limitation or missing integration, assign at minimum Heuristic 7.

IMPORTANT — Assign only the strongly central heuristics, not every one that could loosely apply.
Ask: "What is the PRIMARY usability barrier this issue describes?" Assign that heuristic.
Then ask: "Is there a second barrier that is equally central to the issue, not just tangentially related?"
If yes, assign that too. Stop there unless a third is genuinely co-equal.

Most issues have 1-2 strongly central heuristics. Only assign more when multiple barriers are
explicitly and independently described in the issue.

The test for whether a heuristic is central vs peripheral:
  CENTRAL: Removing this barrier would substantially resolve the issue.
  PERIPHERAL: This heuristic could loosely describe some aspect of the issue, but fixing it
              alone would not resolve the user's problem.

Worked examples of CORRECT (1-2 themes) vs WRONG (4-6 themes) assignment:

  Issue: "Support other KMS keys besides GCP"
  CORRECT:  7. Flexibility and efficiency of use
  (The barrier is that users cannot use the tool with their KMS — a workflow/capability limit.)
  WRONG:    4. Consistency, 6. Recognition, 7. Flexibility, 9. Error diagnosis, 10. Documentation
  (Those others loosely apply but are not the primary barrier.)

  Issue: "Add examples for notation command --help output"
  CORRECT:  10. Help and documentation
  (The barrier is missing documentation/examples in help text.)
  WRONG:    6. Recognition rather than recall, 7. Flexibility, 10. Help and documentation
  (Recognition and Flexibility loosely apply but the core barrier is documentation.)

  Issue: "docs: invalid signing time fail to sign — improve prompt"
  CORRECT:  9. Help users recognize, diagnose, and recover from errors  +  7. Flexibility and efficiency of use
  (Two co-equal barriers: poor error message AND workflow friction when signing fails.)
  WRONG:    1. Visibility, 6. Recognition, 9. Error diagnosis, 10. Documentation, 7. Flexibility

  Issue: "Manual rekor upload with cosign public key" (user confused about process, docs missing, inconsistent behavior)
  CORRECT:  1. Visibility of system status  +  4. Consistency and standards  +  10. Help and documentation
  (Three co-equal barriers explicitly described: unclear status, inconsistent behavior, missing docs.)
  This is an example of a legitimately multi-theme issue — all three are independently described.

NOTE: Integration with external tools always includes Heuristic 7 (Flexibility and Efficiency of Use).
This may co-occur with other central heuristics but does not automatically trigger 3-4 more.

---

HEURISTIC 1: Visibility of System Status
Definition: The system keeps users informed about what is going on through timely feedback.
Identify when: User is unsure if the tool is working, frozen, or finished. System gives no output or unclear non-error output.
Example markers: "The command just hung with no output", "I didn't know if the upload succeeded", "Needs a progress bar for long operations."

---

HEURISTIC 2: Match Between System and the Real World
Definition: The design speaks the user's language, using familiar words and concepts rather than internal jargon.
Identify when: Confusion caused by the tool using internal terminology instead of standard industry terms.
Example markers: "What does [obscure internal term] mean in the flag description?", "Why is this called X when everyone else calls it Y?", "The error message exposed internal variable names."

---

HEURISTIC 3: User Control and Freedom
Definition: Users need a clearly marked emergency exit to leave unwanted states. Supports undo and redo.
Identify when: Users feel trapped in a process or cannot easily reverse an action.
Example markers: "I couldn't cancel the operation with Ctrl+C", "I accidentally signed the wrong artifact and can't undo it", "Need a dry-run flag before performing destructive actions."

---

HEURISTIC 4: Consistency and Standards
Definition: Users should not have to wonder whether different words or actions mean the same thing. Follow platform and industry conventions.
Identify when: Complaints that the tool behaves differently from other tools in the ecosystem, is internally inconsistent, or counterintuitive to use.
Example markers: "This flag works differently here than it does in Docker", "Why does command A use --file but command B uses --path?", "Does not follow POSIX standards for arguments."

---

HEURISTIC 5: Error Prevention
Definition: Good design prevents problems before they happen; presents confirmation options before committing to destructive actions.
Identify when: Users fall into traps the system could have easily identified beforehand. Users ask about consequences of performing an action.
Example markers: "The tool let me upload an invalid signature file without warning", "Should prompt for confirmation before overwriting", "Allowed me to use an expired key."

---

HEURISTIC 6: Recognition Rather Than Recall
Definition: Minimize memory load by making elements, actions, and options visible. Users shouldn't need to remember information across parts of the interface.
Identify when: Complaints about how much users must memorize vs. being prompted. High cognitive load placed on users to complete a task.
Example markers: "I have to constantly check the docs for basic flag syntax", "Lack of tab-completion makes this hard to use", "Help output doesn't show required arguments clearly."

---

HEURISTIC 7: Flexibility and Efficiency of Use
Definition: Design caters to both inexperienced and experienced users; allows tailoring of frequent actions.
Identify when: Workflow blockers. Power users cannot automate/script; new users find simple tasks too complex. Integration limitations with other tools.
Example markers: "Too many steps for a simple sign operation", "Need JSON output so I can pipe this into another tool", "Cannot configure defaults for repetitive flags."

---

HEURISTIC 8: Aesthetic and Minimalist Design
Definition: Interfaces should not contain irrelevant or rarely needed information. Every extra unit competes with relevant information.
Identify when: Complaints about noisy output hiding the actual result the user cares about, or UI/UX friction on the web client.
Example markers: "The default output is too verbose", "Debug logs are printed by default, obscuring the success message", "Help text is a wall of text and hard to scan."

---

HEURISTIC 9: Help Users Recognize, Diagnose, and Recover from Errors
Definition: Error messages should be in plain language, precisely indicate the problem, and constructively suggest a solution.
Identify when: Reports of terse or useless error messages. User cannot tell what went wrong or how to fix it.
Example markers: "The tool just failed with 'Error 500' and no context", "The error message didn't tell me how to fix the certificate issue", "Printed a raw stack trace instead of a human-readable message."
Note: If the issue is about missing information generally (not an error message), use Heuristic 10 instead.

---

HEURISTIC 10: Help and Documentation
Definition: While systems should ideally be self-explanatory, documentation must help users understand how to complete their tasks.
Identify when: Explicit complaints about the quality, existence, or accuracy of the documentation (README, website, or CLI --help text).
Example markers: "The examples in the README don't work", "Documentation is outdated compared to the current CLI version", "Cannot find info on how to use this feature with private registries."

SECTION 8: PHASE 4 — L1_THEME (DETAILED LOW-LEVEL THEMES)
================================================================================

APPLIES TO: Only usability issues (usability_non-usability_type = 1).
Multiple themes per issue are allowed; separate with commas.
Anchor in codes_primary; re-read body_text/comments when needed.

IMPORTANT — Do not leave L1_Theme blank for usability issues: If you have classified an issue as usability,
you MUST assign at least one L1_Theme. There is no valid usability issue with no applicable theme. When in
doubt between two themes, assign both.

---

L1 THEME 1: Missing Feature / Enhancement Request
Description: The user is asking for functionality that does not currently exist, or to enhance existing functionality (except documentation).
Example: "Add support for Ed25519 keys."

---

L1 THEME 2: Unexpected Behavior
Description: The software behaves incorrectly (errors) despite the user following instructions or documentation.
Example: User followed documented steps exactly but received an unexpected result or error.

---

L1 THEME 3: Authentication Friction
Description: The user is unable to log in or authenticate successfully due to token errors, timeouts, or confusing flows. Includes OIDC, MFA, authorization, user groups, and identification issues.
Example: "Token refresh failed", "401 Unauthorized loop."

---

L1 THEME 4: Configuration Friction
Description: The user is struggling to configure the software correctly due to complex setups, rigid settings, or issues that are resolved by correct configuration.
Example: User cannot figure out the correct YAML/JSON configuration to enable a feature.

---

L1 THEME 5: Integration Failure / Issues
Description: The tool fails to interoperate with an external system (a specific Cloud KMS, Registry, or IdP) despite correct configuration. Includes requests for new external integrations.
IMPORTANT: Issues between components of the same tool ecosystem are NOT integration issues. For example, a Fulcio integration issue within cosign is not an integration issue; a cosign integration issue with an external S3 bucket is.
Example: "Azure KeyVault plugin timeout", "Docker Registry API 404."

NOTE — Feature requests for new integrations: If a user requests support for a new external system that is not
yet supported (e.g., "Support other KMS keys besides GCP", "Add --file-ca flag to take secrets from files like
Fulcio does"), assign both this theme AND "Missing feature / enhancement request". The request is both a functional
gap and an integration concern.

---

L1 THEME 6: User Confusion / Unclear Documentation / Documentation Improvements
Description: The user does not understand how to use the tool (asking questions or confused), the documentation misleads or is insufficient, or there is a need to improve documentation.
Example: "How do I sign a blob?", "Docs say flag X exists but it doesn't."

NOTE — Documentation improvements as standalone issues: If an issue is specifically requesting that documentation
be improved, expanded, or corrected (even with no reported user confusion in the issue itself), still assign this
theme. Examples: "Add examples for notation command help doc", "add info to readme file to point out other doc files",
"Clean up blob sign/verify specs in v1.1.1". These are documentation improvement requests and belong here.

---

L1 THEME 7: Build/CI/Installation/Distribution Release Issues
Description: The tool fails to run or install in an automated environment, fails to compile, or the distribution release cannot be assessed/installed.
Example: "Go toolchain version mismatch", "CI pipeline fails on test."

---

L1 THEME 8: Performance Issue
Description: The tool is functionally working but is too slow, consumes too much memory, or has high latency. Includes enhancement requests to address these deficiencies.
Example: "Verification takes 30 seconds."

---

L1 THEME 9: Security Concerns
Description: A report of a vulnerability (CVE), an unsafe default, or a request to harden security posture.
Example: "Weak crypto default", "Secret leaked in logs."

---

L1 THEME 10: Notification / Logging / Web UI Issues
Description: Issues regarding error messages, logging messages, or Web UI (web client) feedback that are not helpful in resolving problems, or similar concerns.
Example: Notification text is unclear; log output does not indicate root cause; web client UI is difficult to navigate.

---

L1 THEME 11: Tedious Workflows
Description: Users must perform many operations to achieve one purpose; the tool imposes too many requirements to accomplish a task.
Example: "I have to run 5 separate commands just to sign a single artifact."

SECTION 10: PHASE 5 — ASSOCIATED COMPONENT THEME
================================================================================

APPLIES TO: Only usability issues. Read the Associated Component column and map each component to a theme below. Multiple components = multiple themes. Separate with commas.

IMPORTANT — Do not leave Component Theme blank for usability issues: If you have classified an issue as usability,
you MUST assign at least one component theme. Default to "Core" when no more specific theme fits.

IMPORTANT — Assign the surface WHERE the issue manifests, not every component the fix might touch.
This is the single most common error: assigning 3-5 themes because the issue discusses signing, verification,
and documentation, when the issue is actually about one surface (e.g., the --help output).

The test: "What is the ONE thing a developer would have to open or change to resolve this issue?"
  - If they'd edit the CLI help text → CLI Tooling (not also Signing Workflow + Verification Workflow)
  - If they'd edit a README or spec file → Core (documentation lives at the tool level, not a workflow)
  - If they'd change the signing code path → Signing Workflow
  - If they'd change auth/token handling → Authentication/Authorization Tools
  - If it's unclear which single component → Core

Worked examples of CORRECT assignment (1-2 themes) vs WRONG assignment (3-5 themes):

  Issue: "Add examples for notation command --help output"
  CORRECT: CLI Tooling  (the surface is the CLI help text)
  WRONG:   CLI Tooling, Signing Workflow, Verification Workflow, Key Management Core

  Issue: "SkippedByTrustPolicy status in JSON output of notation verify is undocumented"
  CORRECT: CLI Tooling  (the surface is CLI output and its documentation)
  WRONG:   CLI Tooling, Verification Workflow, Policy/configuration, Notification/Logging

  Issue: "Support other KMS keys besides GCP"
  CORRECT: Core  (broad tool-level integration gap, no single workflow component)
  WRONG:   Authentication/Authorization Tools, Core, API

  Issue: "add info to readme file to point out other doc files"
  CORRECT: Core  (documentation at the tool level)
  WRONG:   CLI Tooling, Signing Workflow, Notification/Logging

Only assign multiple themes when the issue is explicitly and separately about two distinct surfaces.
Example of legitimately multiple: "notation sign fails with 401 AND the error message gives no guidance"
→ Authentication/Authorization Tools (the 401), Notification/Logging (the poor error message).

---

COMPONENT THEME 1: Authentication / Authorization Tools
Description: Identity verification (login) and permission-granting processes. Covers OIDC flows (client-side and provider-side), token handling, MFA, and RBAC logic.
Applies to: Components marked with Authentication, Auth, OIDC, or similar.

---

COMPONENT THEME 2: CLI Tooling
Description: Issues specific to the command-line interface as the point of interaction. Flag parsing logic, help output text, terminal UX, output formatting (JSON vs text), interactive prompts.
Applies to: Any issue where the affected surface is a CLI command (e.g., "cosign sign", "vault sign").

---

COMPONENT THEME 3: Signing Workflow
Description: The end-to-end client-side process a user performs to cryptographically sign an artifact.
This includes not only the act of signing itself but also anything directly involved in enabling signing:
key loading, signer configuration, signing credential handling, and signing-related API methods or flags.
Applies to: Issues where the key idea is that the user is trying to sign, OR where the subject involves
signing keys, signers, signing credentials, or signing-related capabilities — even if framed as an
API request, flag addition, or configuration change.

Examples that ARE Signing Workflow (even if they look like API or configuration issues):
  - "Allow Rekor's ephemeral signer to load a key from file" → the signer and its key loading is part
    of the signing workflow, even though it mentions a flag and testing configuration.
  - "Expose entry's public key/certificate via a direct API method" → public keys and certificates are
    signing artifacts; the surface a user depends on to complete the signing/verification chain.
  Do NOT use Core or API for these — the signing material is the signal.

---

COMPONENT THEME 4: Verification Workflow
Description: The end-to-end client-side process a user performs to validate a signature.
Applies to: Issues where the key idea is that the user is trying to verify.

---

COMPONENT THEME 5: Policy / Configuration
Description: How the tool is configured by the user or administrator. Includes syntax/logic issues in config files (YAML/JSON), defining and enforcing security policies (OPA/Rego), and interpretation of settings.
Applies to: Struggles with configuration files or policy definitions.

---

COMPONENT THEME 6: Build / CI / Installation
Description: Friction when running, installing, or using the tool in automated, non-interactive environments (CI/CD pipelines, containerized builds, automated scripts).
Applies to: GitHub Actions failures, Docker build issues, installation failures.

---

COMPONENT THEME 7: Release Pipeline
Description: Issues related to how project maintainers build, sign, and publish official releases, binaries, and artifacts of the tools themselves.
Applies to: Issues about the tool's own release process, not user workflows.

---

COMPONENT THEME 8: Notification / Logging
Description: Output generated by the tools for human consumption or operational monitoring. Clarity, verbosity, and actionability of error messages, warnings, informational status, and debug traces.
Applies to: User complains log output is unclear, missing, or misleading.

---

COMPONENT THEME 9: Core
Description: Issues affecting the overall/core tool when it is unclear which specific component is being
affected, or when the issue spans the tool broadly without a single identifiable surface.
Applies to: Use when no more specific theme applies.

NOTE on Core vs Key Management Core: Both themes contain the word "core". If the human label is simply
"core" (meaning unclear/general), assign Core (Theme 9). Key Management Core (Theme 12) is only
appropriate when the issue is specifically about cryptographic key storage, HSMs, or secrets management
infrastructure — not just any broad or unclear issue. When in doubt between the two, prefer Core.

---

COMPONENT THEME 10: API
Description: Issues affecting the REST APIs of the tools or their API endpoints.
Applies to: User interacting with the tool's API, not CLI or UI.

---

COMPONENT THEME 11: Web Client
Description: Issues affecting the web UI, client, or admin dashboard of these tools.
Applies to: User reports a problem on the web-based interface.

---

COMPONENT THEME 12: Key Management Core / Secrets Backend
Description: Infrastructure for secure storage, generation, retrieval, and lifecycle management of cryptographic keys and secrets. Covers integrations with external KMS (HashiCorp Vault, AWS KMS, GCP KMS), HSMs, and local secure storage (keychains, YubiKeys).
For Vault secret engines specifically: note this in parentheses.
Example: (Authentication, Key Management Core (secret engine))

VAULT-SPECIFIC NOTE: When the usability surface is a Vault secret engine, mark component theme as "Key Management Core (secret engine)" in addition to any other applicable themes.

SECTION 11: TRAINING PHASES & ANNOTATION PROCESS
================================================================================

Annotation is conducted in sequential phases with iterative calibration between human annotators and you (the LLM classifier). The goal is to reach agreement before coding the held-out evaluation set.

PHASE 1
Target columns: Associated Component, codes_primary
Process: Train on the first 100 issues in batches of 25. Output your labels; receive human feedback; iterate until alignment is satisfactory. Then review the 100 labelled issues. Finally, code the held-out 60 issues (issues 102-161) for agreement measurement.

PHASE 2
Target column: usability_non-usability_type
Process: Follow the same batch training process. Label issues as usability (1) or non-usability (0). Calibrate against human labels before final coding.

PHASES 3-5
Target columns: L1_Theme, L1_Theme Secondary, Associated Component Theme, Nielsen_Theme
Process: Follow the same process for each column in turn. Only label usability issues. Multiple labels per column are allowed.
